# Task Tracker

## Назначение
REST API сервис для управления задачами внутри команд с ролевой
моделью, историей изменений, кешированием списка задач и SQL отчетом

### Описание
Сейчас реализованы:

- HTTP-сервер с проверкой состояния GET /api/v1/health.
- Регистрация пользователей с сохранением в MySQL и хешированием паролей bcrypt.
- Вход с выдачей JWT, проверка токенов через middleware.
- Создание команд вместе с владельцем в одной транзакции, список своих команд.
- Добавление зарегистрированных пользователей в команду по email с проверкой роли инициатора.
- Смена ролей участников владельцем команды с защитой роли owner.
- Создание и обновление задач с проверкой прав автора и исполнителя.
- Фильтрация задач и пагинация списков команд, задач, истории и комментариев.
- История создания и изменений задачи, сохраняемая в одной транзакции с задачей.
- Проверка версии при обновлении для защиты от потери конкурентных изменений.
- Добавление и чтение комментариев участниками команды задачи.
- Валидация запросов и единый JSON-формат ошибок.
- Request ID, логирование HTTP-запросов и восстановление после panic.
- Конфигурация через YAML и переменные окружения, корректное завершение приложения.

Redis-кеш и SQL-отчёт запланированы. Redis запускается через Compose,
но приложение пока его не использует.

## Авторизация

Регистрация:

```bash
curl -i http://localhost:8080/api/v1/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com","name":"User","password":"example-password"}'
```

Успешный ответ: 201 с полями id, email, name, created_at.
Повторный email возвращает 409.

Вход:

```bash
curl -i http://localhost:8080/api/v1/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"user@example.com","password":"example-password"}'
```

Успешный ответ: 200 с телом `{"token":"<JWT>"}`.
Неверные учётные данные возвращают 401.

Для защищённых маршрутов токен передаётся в заголовке:

    Authorization: Bearer <JWT>

Маршруты команд, задач, истории и комментариев требуют этот заголовок.
Регистрация, вход и health доступны без токена.

Ошибки возвращаются в формате `{"error":"..."}`.
Некорректный запрос возвращает 400, превышение лимита JSON в 64 КиБ — 413,
внутренняя ошибка — 500.

## Маршруты API

Все пути ниже указаны относительно `/api/v1`. ID передаются в формате UUID.

| Метод | Путь | Действие | Успешный ответ |
|-------|------|----------|----------------|
| GET | `/health` | Проверка состояния | 200, текст `OK` |
| POST | `/register` | Регистрация | 201 |
| POST | `/login` | Получение JWT | 200 |
| POST | `/teams` | Создание команды | 201 |
| GET | `/teams` | Свои команды с пагинацией | 200 |
| POST | `/teams/{id}/invite` | Добавление участника | 201 |
| PATCH | `/teams/{id}/members/{user_id}/role` | Смена роли | 204 |
| POST | `/tasks` | Создание задачи | 201 |
| GET | `/tasks` | Задачи команды с фильтрами и пагинацией | 200 |
| PUT | `/tasks/{id}` | Обновление задачи с проверкой версии | 200 |
| GET | `/tasks/{id}/history` | История задачи с пагинацией | 200 |
| POST | `/tasks/{id}/comments` | Добавление комментария | 201 |
| GET | `/tasks/{id}/comments` | Комментарии с пагинацией | 200 |

## Пагинация

Списки команд, задач, истории и комментариев принимают query-параметры:

| Параметр | По умолчанию | Допустимые значения |
|----------|--------------|---------------------|
| `limit` | 20 | Целое от 1 до 100 |
| `offset` | 0 | Неотрицательное целое |

Отсутствующий параметр получает значение по умолчанию. Пустой параметр,
например `?limit=`, нечисловое значение, переполнение или выход за диапазон
возвращают 400. Явный `limit=0` также возвращает 400.

Все списки возвращают объект страницы:

```json
{
  "items": [],
  "total": 293,
  "limit": 20,
  "offset": 300
}
```

`total` — общее количество доступных записей по текущим фильтрам до пагинации.
Если `offset` выходит за конец списка, `items` остаётся пустым массивом,
а `total` сохраняет значение. Чужие команды и задачи не учитываются в выдаче
пользовательских списков. Для истории и комментариев сначала проверяется доступ
к задаче; при отказе количество записей не возвращается.

Порядок списков — `created_at DESC, id DESC`. Данные могут изменяться между
запросами страниц. Число страниц вычисляется как `ceil(total / limit)`.

## Команды

В примерах TOKEN — JWT из ответа входа, TEAM_ID — UUID созданной команды.

```bash
curl -i http://localhost:8080/api/v1/teams \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Моя команда"}'

curl -i 'http://localhost:8080/api/v1/teams?limit=20&offset=0' \
  -H "Authorization: Bearer ${TOKEN}"

curl -i "http://localhost:8080/api/v1/teams/${TEAM_ID}/invite" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"email":"member@example.com","role":"member"}'
```

Создание возвращает 201 с полями id, name, created_at, created_by.
Создатель автоматически становится владельцем. Список возвращает 200 с объектом
страницы `items/total/limit/offset`. В `items` находятся команды текущего
пользователя; при отсутствии команд — `[]` и `total: 0`.

Приглашать могут owner и admin своей команды. Допустимые роли нового участника —
admin и member; назначить owner через приглашение нельзя. Пользователь должен
быть зарегистрирован. Успешный ответ — 201 с team_id, user_id, role, joined_at.
Отсутствующий или недействительный токен возвращает 401, недостаточные права — 403,
неизвестный email — 404, повторное членство — 409. Несуществующая команда также
возвращает 403, поскольку инициатор не имеет в ней членства.

### Смена роли участника

Менять роли может только владелец команды. Допустимые значения —
`admin` и `member`. Изменять роль владельца и назначать нового `owner`
через этот endpoint нельзя. Повторное назначение текущей роли успешно.

`TOKEN` — JWT владельца, `TEAM_ID` — UUID команды,
`USER_ID` — UUID участника, которому меняют роль.

```bash
curl -i -X PATCH \
  "http://localhost:8080/api/v1/teams/${TEAM_ID}/members/${USER_ID}/role" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"role":"admin"}'
```

Успешный ответ — 204 без тела.

| Код | Причина |
|-----|---------|
| 400 | Некорректный UUID, JSON или недопустимая роль |
| 401 | Отсутствующий или недействительный токен |
| 403 | Инициатор не владелец либо изменяется роль владельца |
| 404 | Целевой участник не найден в команде |
| 413 | Превышен лимит JSON в 64 КиБ |
| 500 | Внутренняя ошибка |

Маршрут добавлен для реализации требования управления ролями;
отдельный endpoint смены роли в исходном ТЗ не указан.

## Задачи

В примерах `TOKEN` — JWT, `TEAM_ID` — UUID команды, `TASK_ID` — UUID задачи.
Создавать задачи и читать список могут участники соответствующей команды
с ролями `owner`, `admin` и `member`.

### Создание

```bash
curl -i http://localhost:8080/api/v1/tasks \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d "{\"team_id\":\"${TEAM_ID}\",\"title\":\"Подготовить отчёт\",\"description\":\"Собрать результаты\"}"
```

Поля запроса: обязательные `team_id` и `title`, необязательные `description`
и `assignee_id`. Исполнитель, если указан, должен состоять в той же команде.
Отсутствующий `assignee_id` или `null` создаёт задачу без исполнителя.
Автор определяется по JWT. Начальные значения — `status: "todo"`, `version: 1`,
`closed_at: null`.

У заголовка обрезаются пробелы по краям; допустимо от 1 до 255 Unicode-символов.
Описание может быть пустым и сохраняется с исходным форматированием;
максимальная длина — 65535 байт. Общий лимит JSON-запроса — 64 КиБ,
поэтому доступный размер текста в HTTP-запросе меньше этого лимита
с учётом остальных полей и JSON-кодирования.

Успешный ответ — 201 с полями `id`, `team_id`, `created_by`, `assignee_id`,
`title`, `description`, `status`, `created_at`, `updated_at`, `closed_at`, `version`.
Nullable-поля возвращаются как `null`, если значения нет. Даты выдаются в UTC
в формате RFC 3339 с точностью хранимого значения до миллисекунд.

### Список и фильтры

```bash
curl -i --get http://localhost:8080/api/v1/tasks \
  -H "Authorization: Bearer ${TOKEN}" \
  --data-urlencode "team_id=${TEAM_ID}" \
  --data-urlencode 'status=todo' \
  --data-urlencode 'limit=20' \
  --data-urlencode 'offset=0'
```

`team_id` обязателен. Необязательные фильтры — `status` и `assignee_id`.
Допустимые статусы: `todo`, `in_progress`, `done`. Фильтры действуют одновременно
и применяются также к `total`. Успешный ответ — 200 с объектом страницы.
Пользователь без членства в запрошенной команде получает 403.

### Обновление и права

Обновление выполняется через **PUT**. Передаются текущая `version` задачи
и поля, которые нужно изменить; отсутствующие поля сохраняют прежние значения.

```bash
curl -i -X PUT "http://localhost:8080/api/v1/tasks/${TASK_ID}" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"version":1,"title":"Подготовить итоговый отчёт","status":"in_progress"}'
```

| Кто меняет задачу | Разрешённые поля |
|------------------|------------------|
| Автор, состоящий в команде | `title`, `description`, `status`, `assignee_id` |
| Исполнитель, состоящий в команде | Только `status` |
| Другой участник | Обновление запрещено |

Если пользователь одновременно автор и исполнитель, действуют права автора.
Роли команды `owner/admin` сами по себе не дают права редактировать чужие задачи.
Исполнителю запрещено передавать поля автора даже со значениями, совпадающими
с текущими. Проверки значений совпадают с правилами создания задачи.

Для назначения исполнителя передай UUID участника команды. Для снятия — `null`:

```bash
curl -i -X PUT "http://localhost:8080/api/v1/tasks/${TASK_ID}" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"version":2,"assignee_id":null}'
```

| `assignee_id` в запросе | Результат |
|------------------------|-----------|
| Отсутствует | Сохранить исполнителя |
| UUID | Назначить участника команды |
| `null` | Снять исполнителя |

Для очистки описания передай `"description": ""`. В текущем DTO `null` для
`title`, `description` и `status` трактуется как отсутствие поля.

При переходе в `done` устанавливается `closed_at`. При редактировании уже
закрытой задачи дата сохраняется; при переходе обратно в `todo` или
`in_progress` очищается. Текущая реализация допускает переходы между всеми
тремя статусами с учётом прав пользователя.

Успешный ответ — 200 с обновлённой задачей. Фактическое изменение увеличивает
версию на 1 и обновляет `updated_at`. Запрос без изменений возвращает текущую
задачу без увеличения версии и без новой истории, после проверки прав и версии.

SQL-обновление проверяет версию атомарно. При устаревшей версии возвращается
409; задача и история не изменяются этим запросом. Получи актуальную задачу
через список и согласуй изменения перед повторной отправкой. Новую версию
после успешного обновления бери из ответа.

### История изменений

```bash
curl -i "http://localhost:8080/api/v1/tasks/${TASK_ID}/history?limit=20&offset=0" \
  -H "Authorization: Bearer ${TOKEN}"
```

Историю могут читать участники команды задачи. Успешный ответ — 200
с объектом страницы. Каждая запись содержит `id`, `task_id`, `changed_by`,
`changes`, `created_at`. Пример поля `changes`:

```json
{
  "title": {"old": "Черновик", "new": "Итоговый отчёт"},
  "status": {"old": "todo", "new": "in_progress"},
  "assignee_id": {"old": null, "new": "11111111-1111-4111-8111-111111111111"}
}
```

При создании записываются начальные значения заголовка, описания, статуса
и исполнителя с `old: null`. При обновлении записываются только фактически
изменённые поля. Сохранение задачи и истории выполняется в одной транзакции:
ошибка записи истории откатывает изменение задачи.

## Комментарии

Добавлять и читать комментарии могут все участники команды задачи.

```bash
curl -i "http://localhost:8080/api/v1/tasks/${TASK_ID}/comments" \
  -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/json' \
  -d '{"body":"Отчёт готов к проверке"}'

curl -i "http://localhost:8080/api/v1/tasks/${TASK_ID}/comments?limit=20&offset=0" \
  -H "Authorization: Bearer ${TOKEN}"
```

`body` обязателен; пустой или состоящий только из пробельных символов текст
возвращает 400. Максимум — 65535 байт с учётом общего HTTP-лимита JSON в 64 КиБ.
Форматирование текста сохраняется. Автор определяется по JWT.

Добавление возвращает 201 с полями `id`, `task_id`, `created_by`, `body`,
`created_at`. Список возвращает 200 с объектом страницы. Добавление комментария
не меняет версию, дату обновления и историю задачи.

## Ошибки задач, истории и комментариев

Ошибки имеют вид `{"error":"..."}`. Внутренние диагностические сообщения
клиенту не передаются.

| Код | Причина |
|-----|---------|
| 400 | Некорректный UUID, JSON, текст, статус, версия или параметры пагинации; исполнитель не состоит в команде |
| 401 | Отсутствующий, истёкший или недействительный JWT |
| 403 | Нет членства в команде либо прав на изменение запрошенных полей |
| 404 | Задача не найдена |
| 409 | Версия задачи устарела при обновлении |
| 413 | Превышен лимит JSON-запроса в 64 КиБ |
| 500 | Внутренняя ошибка |

## Проверки

Тесты находятся в `tests/`, структура каталогов повторяет `internal/`:
например, `tests/service/` и `tests/storage/mysql/`. Они проверяют пакеты
через публичный API. Тест SQL-отчёта будет размещён рядом с его реализацией
в `internal/storage/mysql/`. Команда `go test ./...` запускает обе группы.
`make test` и CI используют `-coverpkg=./internal/...`, чтобы учитывать
покрытие рабочего кода тестами из отдельных каталогов.

В терминале devcontainer:

```bash
make test
make lint
go build ./...
```

MySQL-интеграции запускаются при заданном MYSQL_TEST_DSN.
Без него они пропускаются. Для подключения к MySQL из devcontainer:

```bash
MYSQL_TEST_DSN="${DB_USER}:${DB_PASSWORD}@tcp(mysql:3306)/${DB_NAME}" \
  go test -race -count=1 ./...
```

конкретные тесты
```bash
MYSQL_TEST_DSN="${DB_USER}:${DB_PASSWORD}@tcp(mysql:3306)/${DB_NAME}" \
  go test -v -race -count=1 -run '^TestTeamStats$' ./internal/storage/mysql
```
или
```bash
MYSQL_TEST_DSN="${DB_USER}:${DB_PASSWORD}@tcp(mysql:3306)/${DB_NAME}" \
  go test -v -race -count=1 -run '^TestTeamStats/top_ties$' ./internal/storage/mysql
```

Redis-интеграции запускаются при заданном `REDIS_TEST_ADDR`; пароль передаётся
через `REDIS_TEST_PASSWORD`. Тест совместной работы MySQL и Redis требует
настроек обоих подключений. Для запуска всех тестов со сбором покрытия
из devcontainer (переменные `DB_USER`, `DB_PASSWORD`, `DB_NAME` и
`REDIS_PASSWORD` должны быть доступны в окружении терминала):

```bash
MYSQL_TEST_DSN="${DB_USER}:${DB_PASSWORD}@tcp(mysql:3306)/${DB_NAME}" \
REDIS_TEST_ADDR=redis:6379 \
REDIS_TEST_PASSWORD="$REDIS_PASSWORD" \
  make test
```

`make test` создаёт `coverage.out`. Покрытие по функциям и общий процент
в строке `total` можно посмотреть командой:

```bash
go tool cover -func=coverage.out
```

Для просмотра покрытия строк в браузере сформируйте HTML-отчёт:

```bash
go tool cover -html=coverage.out -o /tmp/task-tracker-coverage.html
```

Откройте полученный файл в браузере. Если настройки интеграционных тестов
не заданы, соответствующие проверки отмечаются `SKIP`, а не ошибкой.
Функции репозитория, которые проверяются только интеграционными тестами,
тогда могут показывать `0.0%`: их код не выполнялся. Это не означает,
что тестов для них нет. Покрытие отражает последний запуск, создавший
`coverage.out`; для оценки с учётом интеграций используйте команду выше.

Интеграционные тесты используют временные таблицы либо отдельные таблицы
со случайным префиксом и удаляют их после проверки. Для задач, истории
и комментариев применяются реальные миграции и внешние ключи к изолированным
таблицам. Нужны права CREATE TABLE и DROP TABLE. Существующие записи приложения
не изменяются; root-доступ для тестов не нужен.

Проверяются права на поля и доступ к спискам, фильтры и пагинация, состояния
исполнителя и даты закрытия, JSON истории, откат транзакций, а также два
конкурентных обновления одной версии: сохраняется один запрос и одна запись
истории, второй получает конфликт.

## Логи приложения в devcontainer

При `ENV=local` приложение пишет логи в stdout и `tmp/app.log`.
Для просмотра в терминале VS Code:

```bash
tail -f tmp/app.log
```

`tmp/build-errors.log` содержит ошибки сборки Air.
